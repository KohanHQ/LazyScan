# Summary

Added **CBZ/ZIP chapter upload** (web-only, client-side unzip via `fflate`). An
uploader can drop a comic archive and have its image pages extracted in the
browser, then fed into the **existing** page-by-page upload flow unchanged
({filename, contentType, sizeBytes} → presigned PUT → image-svc convert →
outbox). The server is untouched: it already natural-sorts by filename
(`chapter.service.ts:95`, `Intl.Collator` `numeric:true`) and assigns page
numbers, so CBZ is purely a new way to *acquire* the `File[]`.

Decision trail earlier in the session (see also `nice-to-have.md`):
- Reviewed legacy `LazyScan-Stack` backlog vs the trimmed repo; confirmed webtoon
  scroll + library advanced filter already shipped here (divergence), CBZ genuinely
  absent. CBZ picked as highest-leverage feature for the uploader-centric flow.
- **Unzip client-side, sort server-side.** Server-side unzip rejected: the 1.9 GB
  shared VPS would buffer a 100–300 MB archive in the API process; client unzip
  keeps bytes off the API and reuses the presign-direct-to-R2 path.
- OTel/observability re-raise parked push-only P3 (Dozzle already covers the infra
  layer; self-host triad too heavy for the 1.9 GB box).

# Files Touched

- `web/package.json`, `web/bun.lock` (`2206a51`) — add `fflate@0.8.3`.
- `web/src/utils/cbz.ts` (`2206a51`, new) — `extractCbz` (async, off-thread,
  filters non-image entries before inflate), `isArchiveFile`, `isImageEntry`,
  `normalizeEntryName`, `cbzSupported` (desktop gate: `pointer:fine` +
  `min-width:1024px`), `MAX_ARCHIVE_BYTES` (250 MB pre-unzip cap = real OOM guard).
- `web/src/test/utils.cbz.test.ts` (`2206a51`, new) — 51 assertions: archive/image
  detection, name normalization, extraction (filters `__MACOSX/`/dotfiles/
  `ComicInfo.xml`/dirs), nested-path preservation, no-images / corrupt / oversize
  throw paths.
- `web/src/pages/manage-chapter.ts` (`2206a51`) — selection resolved at pick time
  into a `SelectedPages` holder (`resolveSelection`): single archive → unzip, else
  loose files; submit reads the holder, not the raw input FileList. `accept` + hint
  adapt to `cbzSupported()`. Archive errors / unsupported devices / mixed selection
  clear the selection and surface a message instead of failing at submit.
- `.gitignore` (`2206a51`) — ignore `.coderabbit.yaml` (local review artifact).

# Decisions

- **Filename = normalized entry path** (not basename): keeps inner dirs so the
  server's numeric sort orders nested archives correctly and dup basenames across
  folders stay unique; flat archives (the norm) reduce to the bare filename.
  Verified `File.name` preserves `/` in the unit test.
- **Per-page 10 MB cap** unchanged — a fat page still fails the whole import
  (existing behavior).

- Streaming/worker unzip (v2) — **not planned.** Its only value is dropping the

  CBZ-only gate (loose page-by-page still works on mobile) makes it moot. Also
  would force a 2-pass zip read or an API contract change (current flow presigns
  all pages upfront from a known `files[]`), eroding the web-only win. Revisit
  ONLY if "uploaders demand CBZ on mobile" becomes real.
- CBR/RAR — no good pure-JS lib; CBZ/ZIP only.

# Summary

Owner can now upload an animated GIF as their avatar; the web profile renders the
animation. Implemented as the smallest safe change: a GIF is stored as-is (the
image-svc `/convert` path only emits static WebP, which would drop the
animation); every other format keeps converting to a static 512px WebP. Decided
with the user against transcoding to animated WebP (would touch the load-bearing
`convert.go` shared with chapter pages + needs unverified libvips anim support).

# Files Touched

- `api/src/modules/upload/upload.service.ts` — `createAvatarUpload` branches on
  `file.type === "image/gif"`: size cap (reuses `MAX_IMAGE_UPLOAD_BYTES`),
  magic-byte sniff (`isGifBuffer`, GIF87a/89a, `>= 10` bytes), stored raw at
  `avatars/{userId}.gif` (content-type `image/gif`); GIF dims read from the
  header (`readGifDimensions`). Best-effort delete of the stale `.webp`/`.gif`
  counterpart on a format switch to keep the no-orphan invariant.
- `web/src/pages/profile.ts` — avatar file input `accept` adds `image/gif`; copy
  notes animated GIFs are kept as-is.

# Previous Behavior

Avatar upload rejected GIF (MIME allowlist in `validateAndProcessImage`); all
avatars converted to static WebP at `avatars/{userId}.webp`.

# New Behavior

GIF avatars stored as-is and animate in the `<img>` slot (`renderCover`,
`.profile-avatar` is `object-fit:cover`, not a `background-image` crop — no render
change needed). Static PNG/JPEG/WebP path unchanged.

# Reason For Change

`nice-to-have.md` P2 — Animated GIF owner avatar. Owner-only (single object), so
storing the unresized GIF is a non-issue.
